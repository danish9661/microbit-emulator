Docs

One bench, two layers: the chip core runs your firmware, the virtual board answers it. Below: how to run it, how to drive the board, what it supports, how it is built, and how to check a run.

Run firmware

  1. Load a .hex or .bin built for flash 0x0 with ARM GCC and no SoftDevice — or pick a preset from the bench. The loader parses Intel HEX (type-02 and type-04 addressing, up to 512 KB) and collects 0x1000xxxx records as UICR bytes for later; a .bin loads raw at zero. Staging parses and holds the image; nothing executes yet.
  2. Press Run. Staging boots through the same bootImage path as a dropped file: re-register taps, build the model, create the CPU from the vector-table SP/PC, load firmware at zero, enable IRQ delivery, apply UICR words. The status line names the vectors it booted.
  3. For stock MicroPython, press Boot MicroPython app: the page re-inits pristine (frames between load and click leave dirty timers and NVIC state), re-applies UICR, hand-installs the MBR parameter page (*(0x20000000)=0x1000, *(0x20000004)=0x1C000) the way a real MBR-to-SoftDevice boot would, sanity-checks the vectors at 0x1C000, and resets the CPU there. Banner follows on the console.

If Run reports nothing staged, Load a file or pick a preset first. If MicroPython reports no vector table, the image at 0x1C000 is blank or erased (0xFFFFFFFF). If it reports no valid app, the SP/PC fail the gate (SP inside 0x20000000–0x20020000, PC inside 0x1C000–0x80000) — the bench refuses to jump into the weeds and says so.

Drive the board

Every control on the bench answers through the same peripheral path real firmware uses — there are no shortcuts.

  • Matrix: the 5×5 grid renders rows sunk low and columns driven high, gated on direction set to output. A toggling latch on an input pin stays dark, exactly as on silicon. Content appears only once firmware constructs the display and starts the TIMER4 strobe.
  • Buttons A and B: pointer down drives the pin low, release returns it high (active-low with pull-ups, P0.14/P0.23). A held button reads pressed across reset because input latches survive re-init.
  • Motion: the Tilt X/Y sliders set the accelerometer in milli-g (Z stays at 1000); Shake randomizes all three axes. The part answers WHO_AM_I, echoes control writes, and pulses data-ready on P0.25 — 60 ms low, 140 ms high — because a stuck low trips the shared KL27 threshold and firmware re-polls.
  • Console: type and press Enter to send. Bytes drip one per consumed event and mirror into the DMA ring, the way silicon paces single-slot RX. Bulk-completing early would stall input, so the bench never does.
  • OLED scope: any edge-I2C firmware talking to address 0x3C on TWIM0 draws into the 128×64 framebuffer on the page.
  • Speedometer: the header shows slice rate plus sustained average since boot. Tight spins burst high while banner progress needs sustained throughput — trust the average.

BLE: is it fully done?

No — and here is the honest boundary, file by file. The firmware-visible contract is complete: every one of the 67 S132 BLE SVC numbers (common 0x60–0x69, GAP 0x70–0x8E, GATTC 0x90–0x99, GATTS 0xA0–0xAC, L2CAP 0xB0–0xB2) is claimed by nrf52833-periph-wasm/src/sd_ble.rs and answered per the header register contracts — no call falls through to a fault, and cargo test (220 green, 11 sd_ble tests incl. byte-offset asserts) plus the headless mock (real SVC bytes, 18/18) plus the live E2E (42/42 over-air checks on two links) prove the whole flow: enable, table build, connect, discovery ×6, read, write, L2CAP, pairing + peer-pairing with passkey, indicate, scan, RSSI, disconnect. The air side is real too: tools/ble_air_bridge.py resolves every job over a Bumble LocalLink against two advertising peers (battery 87 PeerBatt + heart-rate twin 64 PeerHR, distinct addresses), with per-peer routing, serialized ATT bursts, and HCI-RSSI-first sampling. A compiled BLE-enabled image proof also exists: blinky/ble_fw/ble_pairing_fw.c drives the CODAL-BLE-shaped JustWorks flow (ENABLE→GATTS table→CONNECT→GATT→AUTHENTICATE→CONN_SEC_GET→DISCONNECT) end to end natively (cargo test nrf_ble_pairing_fw_markers, 17 BLEP:* markers, 2nd-run clean).

What is genuinely finished:

  • SVC dispatch: all 67 numbers claimed; unknown numbers still fall through to raise_sync untouched (zero-cost when BLE is idle); every return code is S132-verified (NOT_ENABLED / INVALID_CONN_HANDLE / INVALID_STATE / BUSY / NO_TX_PACKETS / CID_IN_USE / DATA_SIZE / NOT_FOUND / INVALID_ADDR / INVALID_PARAM / NO_MEM); RAM-pointer validation on every pointer arg.
  • GAP: enable with RAM-floor report, two-arg evt_get (length query, DATA_SIZE without popping, legacy drain), address get/set, advertising data/params validation, connect with staged air job + CONNECTED (CENTRAL role, real conn_params), disconnect with HCI reason echo, scan with live ADV_REPORT (one per peer, unpacked pad byte), RSSI start/stop/get with HCI-first sampling and src tagging.
  • GATT client: all six discovery kinds (primary/relationship/characteristic/descriptor/attr-info/UUID-read) plus multi-read, plain read with offset, write (REQ + CMD, bytes copied at SVC time), HV confirm; every response carries the gattc envelope head and unpacked pads; 128-bit rows encode null with vendor type.
  • GATT server: service/char/descriptor table with SoftDevice-shaped handles, struct-form VALUE_SET/GET (length query, offset checks, conn 0xFFFF allowed), ATTR_GET, CCCD tracking per link with notify-bit/indicate-bit gating (unsubscribed refuses INVALID_STATE), HVX staging with per-link TX budget.
  • Pairing legs: AUTHENTICATE stages the handshake; all six peer-initiated request events post with conn-first wire bodies; every reply SVC validates against the per-link state machine (accept/passkey/OOB/encrypt); S132 SEC_STATUS codes incl. the 0x29→0x85 fix; AUTH_STATUS carries the conn head; complete/fail post AUTH_STATUS (+CONN_SEC_UPDATE) with bonded/encrypted link state feeding CONN_SEC_GET.
  • L2CAP: dynamic-CID register/unregister with range + capacity checks, TX staging with bytes copied at SVC time, RX echo completion.
  • Multi-link: per-link handles, RSSI, TX budget, security, pairing, CIDs; events carry their conn; pump + bridge + E2E all prove two live links with distinct peers and values.

What is deliberately not done (each is a named, bounded gap — none is a hidden fault):

  • No SMP crypto math: passkeys validate shape (6 ASCII digits) but never encrypt; OOB data zeroes 32 bytes. Bond STORE is real (per-peer LTK/IRK/CSRK/master-id, hit/miss/delete + bridge keys leg) — a sniffer comparing air bytes against silicon would see the crypto difference, not a store difference.
  • Central dial-out plus dial-in accept (PERIPH-role CONNECTED when a peer answers our advertisement); no whitelist/directed advertising.
  • No parameter enforcement: CONN_PARAM_UPDATE / PPCP_SET accept without posting updates; MTU exchange, data-length extension, and PHY update do not exist in S132 SVC form (no SVC numbers for them) and are not synthesized.
  • TX flow is real (tokens refill per air packet + TX_COMPLETE posted; NO_TX_PACKETS still gates staging). Still never posted: USER_MEM_REQUEST/RELEASE, GATTC/GATTS TIMEOUT, SEC_REQUEST, SCAN_REQ_REPORT, RW_AUTHORIZE_REQUEST, SYS_ATTR_MISSING, SC_CONFIRM (their reply SVCs ack SUCCESS without effect).
  • GATTC write accepts only REQ(1)/CMD(2): SIGNED_WRITE(3)/PREP_WRITE(4)/EXEC_WRITE(5) refuse INVALID_PARAM — no queued-write or signed-write path.
  • SoC/MBR SVC numbers (mutex, rand pool, power/clock/PPI监管, ECB/CCM/AAR-adjacent sd_ calls) are unmodeled — out of scope for the BLE face; the on-chip crypto engines keep their own take/complete models.
  • No BLE-enabled stock image: MicroPython ships MICROBIT_BLE_ENABLED: 0 and MakeCode builds here never init the stack, so no shipped firmware exercises this face end-to-end (proven instead by the GCC conformance firmware, the C face, the pairing-fw image, the mock, and the E2E).
  • Virtual air, not RF: two Bumble peers on a LocalLink, not spectrum; RSSI is -50 dBm constant from the virtual controller with adv-sighting fallback; range/interference/whitening do not exist.

If you need one sentence: the BLE contract firmware calls is fully answered and proven over virtual air; the radio physics and the crypto math are not.

How the bench is built

The page runs a loop you can read in one sitting. Each animation frame steps the core five times — cpu.step(20000), tick_peripherals(), then the DMA pump — because duties once per frame starve polled firmware: a one-byte transfer staged at slice zero would wait a hundred thousand instructions for completion. When firmware naps in WFE/WFI, the loop advances virtual time and wakes on a pending interrupt; without that the core sleeps forever at its first idle. Faults break the sub-loop and name the program counter on the status line.

  • Chip core (Rust to WASM): Cortex-M4F plus every nRF52833 peripheral, timed off a single instruction-count clock. Unlisted register offsets read zero and writes are ignored, because real HALs probe reserved registers. Unknown instructions halt loudly — nothing fails quietly.
  • Virtual board (JavaScript): the matrix, the LSM303 motion sensor, the SSD1306 OLED, and the serial line. Each part registers its I2C slaves before init, then answers every frame through take/complete transfers and tap events.
  • EASYDMA pump: firmware stages a transfer, the bench moves bytes between guest RAM and the host, then completes it — UARTE, TWIM, SAADC, PDM, I2S, USBD endpoints, NVMC erases (applied as 0xFF), radio loopback, and BLE SVC jobs (GAP/GATTC/L2CAP staged, resolved over the Bumble bridge or loopback, GATTS answered synchronously). I2C buses belong to the parts, not the generic pump.
  • Reboots: firmware that requests reset via AIRCR is rebooted from the vector table — the app table after a direct-app boot, so MicroPython never falls back into the MBR loop.

Depth probes: every handshake earns a consumer

Handshake status used to mean the registers answer with no timed behavior or no consumer. That second half is now closed: demo/parts/mocks.js holds a live consumer for each one, in the same register-then-poll shape as the board parts. Press Run depth probes on the bench, or run node demo/parts/handshake.mjs headless against the built package — eighteen checks, one per surface:

  • Thermometer, comparator band edges, quadrature knob steps.
  • FIPS-197 AES block, address resolve, CTR plus MIC roundtrip.
  • Audio stream silence and capture, NFC tap with frames, I2C and SPI slave engines, edge-display frames over the SPI tap.
  • ADC limit edges, USB setup packet, radio CRC-error path, flash program plus erase.
  • BLE stack face: real SVC bytes for enable, table build, connect, all six discovery kinds, read, write, L2CAP, pairing plus peer-pairing with passkey, indicate, scan, RSSI, disconnect — with the self-test button running the same flow on loopback in-page.

The KL27 stubs stay handshake by decision: the interface chip is deliberately not emulated, so an empty version frame and a request echo are the whole consumer. The NFC pin-route is modeled (UICR.NFCPINS reserves P0.09/P0.10 + gates field sense); RF physics is not.

Checks before you trust a run

  • Suite green: run cargo test in the crate directory (220 green, both thread modes post-P108; single-threaded stays the gate by convention), node demo/parts/smoke.mjs for the parts, and node demo/parts/handshake.mjs for the handshake mocks (18/18, build the local package first with npm run build:handshake inside demo/). Live BLE: serve the bench, start python3 tools/ble_air_bridge.py --port 18771, then node demo/parts/ble_live_e2e.mjs (42/42 over air) or python3 tools/browser_verify_16.py (blinky + self-test + 16/16 probes).
  • Parallel-test flake (CLOSED P108; open pre-existing before that): two mechanisms, both fixed. (a) Deterministic order-dependence — P105: MPU ENABLE + programmed regions lived in the installed model past the test (filtered mpu mwu unalign failed 10/10 single-threaded pre-fix; exit disarm in the two MPU-programming cpu tests). (b) Cross-thread SYS-swap — P108: the installed SYS pointer was swapped by every boot() with no join while sd_ble unit tests never held BOOT_LOCK (filtered sd_ble mwu parallel failed ~18/20 pre-fix; BOOT_LOCK join in all 11 sd_ble tests). Full suite parallel green post-fix (~30/31 runs; residual is rare scheduling noise, backtrace uncaptured); single-threaded -- --test-threads=1 stays 220/220 and is the gate by convention, not by necessity.
  • Rebuild the package after Rust changes with wasm-pack build into demo/pkg, then serve over HTTP — file:// cannot load the wasm module.
  • Firmware proofs rebuild with the GCC flags in docs/README.md; the C recipe is verified bit-identical.
